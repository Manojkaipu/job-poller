# job-poller

Checks the public job boards of 1,240 companies every hour, keeps the postings whose title and location match what I'm looking for and that went up in the last 24 hours, and emails me the ones it hasn't seen before.

Job sites and LinkedIn alerts often lag the company's own board, and they cover smaller companies unevenly. Most companies post through an applicant tracking system (ATS) that serves its job board from a public JSON endpoint, so polling those directly gets a posting within hours of it going up.

Pure Python standard library, no dependencies.

1,240 companies in three files:

* `companies_yc.toml`, 420 Y Combinator startups hiring in the US, generated by `scripts/import_yc.py` from the [open YC directory](https://yc-oss.github.io/). Of 1,371 YC companies hiring in the US or remotely, 443 have a public board on Ashby, Greenhouse, Lever or Workable that could be confirmed as theirs; the rest post through YC's own Work at a Startup or a site of their own. A listed company whose board empties is moved to Work at a Startup if it posts there (Corgi, Great Question, NanoNets, Remi and Solva so far). Re-run the script every month or two to pick up newly hiring companies.
* `companies_gallery.toml`, 577 startups from [startups.gallery](https://startups.gallery/), generated by `scripts/import_gallery.py`. Each company page on the site links the company's own job board, so nothing is guessed: of 1,358 companies, 868 link a board one of these fetchers reads (directly, or through their own careers page), and 579 of those had a US or remote-US posting and weren't already in the other two files. Two have since lost their boards and were removed (see below).

A full run over all 1,240 boards takes about 6 minutes with 16 fetched in parallel, most of it waiting on Eightfold's rate limit.

## Setup

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev]"   # Python 3.11+
python -m pytest -q
```

Email goes out over SMTP. Put the settings in a `.env` file (gitignored) or the environment:

```
SMTP_USER=you@gmail.com
SMTP_PASSWORD=your-app-password     # Gmail: Google Account > Security > 2-Step Verification > App passwords
MAIL_TO=you@gmail.com,friend@gmail.com   # optional, comma-separated: who gets new postings
ALERTS_TO=you@gmail.com             # optional: who gets "Boards needing attention" (default SMTP_USER)
MAIL_TO_ROBOTICS=her@gmail.com      # optional: the robotics profile's recipient (see Profiles below)
# SMTP_HOST=smtp.gmail.com  SMTP_PORT=465  (defaults; port 587 uses STARTTLS)
```

Without SMTP settings, new postings are just printed. `python -m jobpoller test-email` sends a sample with a few postings that match right now, to check the settings.

## Use

```bash
python -m jobpoller check                    # fetch every board: posting counts, matches, errors
python -m jobpoller list                     # what matches the filters right now
python -m jobpoller list --fresh             # ...and was posted within max_age_hours
python -m jobpoller list --company openai --all
python -m jobpoller run --dry-run            # a real run without saving state or emailing
python -m jobpoller run                      # the scheduled command
python -m jobpoller discover "Company Name"  # which ATS does a company use?
```

**Adding a company.** `discover` tries likely slugs on every supported board and prints the hits with sample titles, so you can tell the right board from a namesake:

```
$ python -m jobpoller discover Retool
Retool: gem slug="retool"  24 postings  https://jobs.gem.com/retool
```

Then add it to `companies.toml`:

```toml
[[company]]
name = "Retool"
ats = "gem"
slug = "retool"
```

`discover` only guesses from the name, and only on the boards with a guessable slug. Workday, Oracle, Eightfold, UKG, Jibe and SuccessFactors need a host or tenant copied from the careers page, and Work at a Startup (`yc`) is only worth trying for a YC company whose own board is empty. When it finds nothing, open the company's careers page and click through to a posting: the URL usually names the ATS and the slug (`jobs.ashbyhq.com/mistral.ai/...`, `cohesity.wd5.myworkdayjobs.com/Cohesity_Careers/...`, `.../hcmUI/CandidateExperience/en/sites/CX_1001/...`). Slugs are often not the company name: Applied Intuition is Ashby `applied`, Gong is Greenhouse `gongio`, Hippocratic AI is Ashby `Hippocratic AI` with the space.

A Workday board can be narrowed with Workday's own search, which matters for boards so big that Workday's 2,000-posting cap cuts them off:

```toml
[[company]]
name = "Walmart"
ats = "workday"
slug = "walmart.wd504.myworkdayjobs.com/WalmartExternal"
search = ["software engineer", "data scientist", "machine learning", "data engineer"]
```

Changing a board's `search` changes which postings it returns, so expect one run of "new" postings from the widened part.

`facets` narrows a Workday board to Workday's own filters instead, such as job categories. The ids are in the `facets` part of any response from the board's `/jobs` endpoint. Salesforce's whole board is ~1,500 postings, mostly sales, about 80 requests, and GitHub's runners got HTTP 429 from it on every run; its Software Engineering, Data and Enterprise Technology & Infrastructure categories are ~160 postings in 8 requests and still hold every posting that matches the filters:

```toml
facets = { jobFamilyGroup = ["14fa3452ec7c1011f90d0002a2100000", "14fa3452ec7c1011f90cf661a7c80000", "14fa3452ec7c1011f90cf8c9c5960000"] }
```

**Filters** are in `config.toml`. A title has to contain one of the `include` terms and none of the `exclude` terms, as whole words: `ml` matches "ML Engineer" but not "HTML". Phrases in `protect` are ignored by the exclude check, so `staff` can be excluded without losing "Member of Technical Staff". Location is checked against US states, state codes, major cities and country names, so "US, CA, Santa Clara", "New York City, NY" and "Remote - US" pass while "London", "Toronto, ON" and "Remote - EMEA" don't. A posting with no location, or plain "Remote", is kept.

**Profiles** give one recipient a wider net than everyone else. A `[[profile]]` in `config.toml` names extra title terms and the environment variable holding its address (a repository secret in CI, since this repo is public). That recipient gets a separate email with everything the base filters match plus postings whose titles hit the extra terms; `exclude_extra` drops noise from the extras only, never from the base matches. The robotics profile adds terms like robotics, humanoid, autonomy, perception, SLAM and robot learning, and excludes operator, technician and analyst roles that those words drag in. Each term was checked against every board: "controls engineer" was left out for matching data-center and power-plant controls, "firmware" for consumer devices and ASICs, "localization" for translation jobs. Keep a profile's address out of `MAIL_TO`, or it gets both emails. `python -m jobpoller test-email --profile robotics` sends that recipient a sample.

## Scheduling

**GitHub Actions** (recommended, since it runs when the laptop is asleep) runs `.github/workflows/poll.yml`. GitHub's own cron is best-effort: for this repo it never started at all in the first five hours. So the real trigger is [cron-job.org](https://cron-job.org), which calls the workflow's `workflow_dispatch` endpoint on a fixed schedule:

* URL `https://api.github.com/repos/<owner>/job-poller/actions/workflows/poll.yml/dispatches`, method `POST`, body `{"ref":"main"}`
* headers `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`, `Content-Type: application/json`
* the token is a fine-grained personal access token limited to this repository with only **Actions: read and write**

A run takes about 6 minutes, so the interval only trades alert delay against load: hourly means ~12-15 emails a day and about 60,000 board requests. The workflow's own cron (every 2 hours) stays as a backup; overlapping triggers queue behind each other and share the state, so nothing is emailed twice. Public repos get unlimited Actions minutes.

Add `SMTP_USER`, `SMTP_PASSWORD` and optionally `MAIL_TO`, `ALERTS_TO` and `MAIL_TO_ROBOTICS` as repository secrets. Everyone on `MAIL_TO` gets the postings; board alerts go only to `ALERTS_TO` (by default the sending account), in their own email when a board crosses its alert threshold. When the two lists are the same it's one email, with any failing boards listed under the postings. The state file is kept in the Actions cache, not committed, so the repo doesn't grow a commit per run. GitHub pauses scheduled workflows in a public repo with no activity for 60 days, and the poller never commits, so `keepalive.yml` re-enables the poll workflow on the 1st of each month.

**Windows Task Scheduler**, if you'd rather run it locally:

```powershell
schtasks /Create /TN JobPoller /SC HOURLY /MO 4 /TR "\"C:\path\to\Job_Poller\scripts\poll.cmd\""
```

`scripts/poll.cmd` runs the poller from the repo's `.venv` and appends to `state\poll.log`.

Use one or the other: each keeps its own state.

## How it works

* **Fetch.** Every board is fetched in parallel (16 at a time, `workers` in `config.toml`), with retries and `Retry-After` handling for rate limits. A board that errors, or changes its format so parsing fails, is skipped for that run without affecting the others.
* **Diff.** `state/seen.json` remembers every posting id per board with when it was first and last seen, including postings the filters rejected. So widening the filters later doesn't report old postings as new.
* **First run is silent.** The first time a board is fetched, its current postings are recorded without alerting, so adding a company with 800 open roles doesn't send 800 alerts. Only postings that appear after that are reported.
* **Only recent postings.** A posting that's new to the poller but that the board says went up more than `max_age_hours` ago (24 by default) is skipped: a re-opened requisition, or one that only just matched. Posted times come from the board where it gives one (Greenhouse, Ashby, Lever, SmartRecruiters, Eightfold, UKG and others, down to the second; Workday's "Posted 3 Days Ago"; YC's "about 23 hours"; Workable, Oracle and SuccessFactors by date). BambooHR, Rippling, Pinpoint, Dover and Manatal publish no date, so there "new to the poller" is the only signal.
* **Outages aren't removals.** A failed fetch leaves the board's known postings untouched, so a 503 followed by a recovery doesn't re-announce everything. A board whose fetch says it's gone (HTTP 404, 410 or 422) is flagged in the email after 3 failed runs in a row, as is a board that suddenly returns 0 postings (usually a moved or renamed board). Any other failure (an HTML maintenance page instead of JSON, a 5xx, a 429, a timeout) is flagged only after 24 runs, about a day: on Oct 17 Workday's maintenance served HTML instead of JSON for ~10 hours, rolling across its customers a few at a time, and every one of the 31 Workday boards crossed the old 3-run threshold. When 3 or more boards on one ATS fail the same way, the email shows them as one line, since that's the ATS, not the boards (`alert_after_failures`, `alert_after_outage` in `config.toml`).
* **Forgetting.** A posting that has been gone for 45 days is dropped from the state; if it's re-posted after that it's reported again. Removing a company from the config drops its state.
* **Email last, save after.** The state is saved only after the email is sent, so a failed send is retried on the next run instead of being lost.
* **Size limit.** A board with more than 5,000 postings is refused as probably not a company (Mercor's contractor marketplace on Manatal has 16,000) rather than paged through for minutes.
* **Partial boards.** Eightfold (Netflix, Qualcomm, Infineon, Lam Research) allows about 20 requests a minute at 10 postings each, so reading Qualcomm's 2,000 postings would take 10 minutes. The limit is per client across every company's Eightfold site, so all Eightfold requests in a run share one 4-second spacing (Netflix, Qualcomm, Infineon and Lam Research together take about 5½ minutes, alongside everything else). Eightfold boards are read one paced page at a time, sorted newest first, and boards over 200 postings are read as a window of the newest 200 (new postings land at the top). Because an older posting can slide into that window when newer ones close, a posting on a partial board only counts as new if its posted date is after the board was first polled.
* **Slow boards in parallel.** Workday serves 20 postings per request, so its pages are fetched 4 at a time: NVIDIA's ~2,000 postings take about 30 seconds.

## Limitations

* Filtering is on title and location only. Descriptions aren't fetched for every board, so "no visa sponsorship" or years-of-experience requirements aren't checked.
* Workday's list gives only a coarse "Posted 3 Days Ago" (a date, never a time, and "30+ Days Ago" for anything older), and caps a listing at 2,000 postings: NVIDIA reports exactly that, so the tail of its board may be missed. `search` terms (as for Walmart) are the workaround.
* Companies that host their own careers site without one of these ATSs (Google, Meta, Apple, Microsoft, Amazon) aren't covered.
* Location parsing is heuristic. "Remote" with no country counts as US; an unusual format may be misread. `extra_locations` and `us_only = false` are the escape hatches.

## How I used AI tools

I used Claude (via Claude Code) to write the fetchers, filters, tests and this README, and to find which board each company uses. The idea, the choice of ATSs and companies, and the filters are mine to tune.

Things that went wrong while building it, and the check that caught each:
* **A board that never ended.** Mercor's Manatal board is its contractor marketplace, with ~16,600 postings served 10 at a time, and the first discovery pass hung on it. Timing each attempt found it; boards over 5,000 postings are now refused, and Manatal is fetched 100 per page.
* **Namesakes.** Name-based discovery found Figure Lending for Figure AI, a UK telesales firm for Together AI, a Dutch hotel group for Clay and a Brazilian bank for Neon. Every hit was checked against its sample titles before going into `companies.toml`.
* **"Hybrid" isn't a place.** Cloudflare's board puts the work arrangement in the location field, so its postings were all rejected as non-US. Listing the engineering postings the filters rejected on boards with suspiciously few matches caught it.
* **Wrong Workday guesses.** Guessed site names for Dell, Qualcomm, Netflix and others returned HTTP 422. Fingerprinting their careers pages showed Dell and Honeywell are on Oracle and Netflix and Qualcomm on Eightfold, which is why those two fetchers exist; Walmart's board was right but lives on a different Workday host (`wd504`).
* **Stale search results.** Web searches pointed Snyk, dbt Labs and Grammarly at Greenhouse boards that now return 404. Every slug was fetched before it went in, so none of those made it into `companies.toml`.
* **"2 Locations".** Workday summarizes multi-city postings as "2 Locations", which the US filter read as a foreign place and dropped. Found by fetching NVIDIA with the new parallel paging; it now counts as an unknown location.
* **Unencoded slugs.** Hippocratic AI's Ashby board name has a space, which the Ashby fetcher sent unencoded. The startups.gallery importer hit the same thing from the other side: links carry the space as `%20`, so slugs are now decoded before use.
* **Boards that move.** Hex moved from Greenhouse to Ashby, Suger rebranded as Fours (Lever `fours`), Faro Health as Faro AI (Workable `faro`, checked against the account's own description since `faro` could be anyone), Within as Klarity (Ashby `within.ai`), and Corgi emptied its Ashby board and now posts only on YC's Work at a Startup. All showed up in the email's "Boards needing attention" section, which is what it's for; the Work at a Startup fetcher exists because of Corgi. Cranston, Anon, Cocoon and Navier AI had no new board to move to and were removed. A hit on `jobs.ashbyhq.com/<name>` proves nothing, since Ashby serves that page for any name; the API's `jobBoard: null` is what says a board is gone.
* **Loose ownership check.** The YC importer first matched a company's name anywhere in a posting with punctuation stripped, so a short name could hide inside another word ("arc" in "research"). Re-checking all 117 short-name hits with whole-word matching found the rule too loose rather than any wrong board; short names now need a whole-word or full-domain match.
